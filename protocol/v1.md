# grantd protocol v1

Status: **frozen at first release**. Any change to canonical bytes, domain
separation strings, ID derivation, or certificate fields is a new protocol
version, not an edit to this document.

One pre-release amendment has been made, before any external consumer existed:
the `answer` field was removed from the agent registration message when the
natural-language captcha was dropped (§11). Test vectors were regenerated and
both implementations re-verified against them.

This document defines the wire protocol byte-for-byte so that two independent
implementations (Go, TypeScript) can be written from the spec alone and agree on
every signature, MAC and identifier. The shared fixtures in
`protocol/test-vectors/` are normative.

---

## 0. Terminology and trust model

| Party | Holds | Trusted for |
|---|---|---|
| **Host** (customer machine) | host identity private key, SSH CA private key, grant secrets | **All authorization decisions.** |
| **Coordination service** (Cloudflare) | public keys, signed grant metadata, redemption envelopes | Routing and rendezvous only. |
| **Visiting agent** | agent identity private key, ephemeral SSH private key | Nothing; must prove possession of a grant secret. |

The coordination service is an **untrusted transport**. Every field it could
tamper with is covered by a signature or MAC that it cannot produce.

---

## 1. Canonical encoding (CBE)

All signed and MAC'd bytes are produced by **Canonical Binary Encoding**. CBE is
used instead of canonical JSON to eliminate the entire class of
canonicalization ambiguities (key ordering, duplicate keys, Unicode escapes,
number formatting, whitespace).

### 1.1 Primitives

```
u32be(n)  := 4-byte big-endian unsigned integer
u64be(n)  := 8-byte big-endian unsigned integer
LP(b)     := u32be(len(b)) || b            ("length-prefixed")
```

### 1.2 Value types

| Tag | Name | Encoding |
|---|---|---|
| `0x01` | STRING | UTF-8 bytes. MUST be valid UTF-8. MUST NOT contain U+0000. |
| `0x02` | U64 | `u64be(v)` — exactly 8 bytes |
| `0x03` | BYTES | raw octets |
| `0x04` | BOOL | one byte, `0x00` or `0x01` |

There is no null, no float, no nested container. Every message is a flat,
ordered list of typed fields.

### 1.3 Message encoding

```
CBE(context, fields) :=
      LP(utf8(context))
   || u32be(count(fields))
   || for each field i, in the order declared by its message schema:
          LP(utf8(name_i)) || tag_i || LP(value_bytes_i)
```

Rules:

* Field order is **the order declared in this document**, never sorted, never
  the order they appear in the JSON envelope.
* Field names are included in the encoding so that a field cannot be shifted
  into another field's position.
* `count(fields)` is the exact number of declared fields. Every declared field
  is always present. There are no optional signed fields in v1.
* `context` is the **domain separation string**. Two different messages can
  never produce identical canonical bytes, and a signature over one context is
  never valid under another.
* Implementations MUST reject a string field that is not valid UTF-8 and MUST
  reject a U64 value greater than 2^63-1 (so that languages with signed 64-bit
  integers cannot disagree).

### 1.4 Domain separation strings

| Constant | Value |
|---|---|
| `CTX_HOST_REGISTER` | `grantd/v1/host-register` |
| `CTX_HOST_CONNECT` | `grantd/v1/host-connect` |
| `CTX_GRANT` | `grantd/v1/grant` |
| `CTX_REDEMPTION_SIG` | `grantd/v1/redemption-agent-sig` |
| `CTX_REDEMPTION_MAC` | `grantd/v1/redemption-proof` |
| `CTX_AGENT_REGISTER` | `grantd/v1/agent-register` |

`CTX_REDEMPTION_SIG` and `CTX_REDEMPTION_MAC` cover the *same field list*. They
differ only in context so that the agent's Ed25519 signature and the grant MAC
are cryptographically distinct objects over the same statement.

## 2. Time

All protocol timestamps are **integer seconds since the Unix epoch, UTC**,
encoded as CBE `U64` and as JSON numbers on the wire. RFC 3339 strings are never
signed. Human-readable timestamps may appear in *unsigned* response envelopes
under a `_rfc3339`-suffixed key and MUST be ignored by verifiers.

Accepted clock skew:

* Host registration / connect / agent registration: `±300` seconds.
* Redemption payload: `±120` seconds.

A verifier MUST reject timestamps outside its window before doing any other
work that depends on the timestamp.

## 3. Keys and identifiers

### 3.1 Key types

All protocol identity keys are **Ed25519**. Raw public keys are exactly 32
bytes. Raw private keys are the 32-byte seed (Go's 64-byte "private key" is
seed||public).

The SSH CA is also Ed25519 but is a **separate key** and is only ever used to
sign SSH certificates. The host identity key is only ever used for CBE
signatures. Neither key is ever used for the other's purpose.

### 3.2 ID derivation

```
id_material(pk)  := SHA-256(pk_raw_32)
b32(b)           := RFC 4648 base32, lowercase alphabet "abcdefghijklmnopqrstuvwxyz234567", no padding
host_id          := "h_" || b32(id_material(host_identity_pub)[0:20])
agent_id         := "a_" || b32(id_material(agent_identity_pub)[0:20])
```

`b32` of 20 bytes is exactly 32 characters, so `host_id` and `agent_id` are
always exactly 34 characters matching `^[ha]_[a-z2-7]{32}$`.

IDs are **self-certifying**: any party that has the public key MUST verify that
the claimed ID equals the derived ID before trusting anything else in the
message.

### 3.3 Grant identifiers and secrets

```
grant_id      := "g_" || b32(random 10 bytes)          -> "g_" + 16 chars, matches ^g_[a-z2-7]{16}$
grant_secret  := 32 bytes from a CSPRNG
secret_text   := base64url(grant_secret), no padding   -> 43 chars, matches ^[A-Za-z0-9_-]{43}$
```

The grant secret is the **only** bearer authority in the system. It is created
on the host, stored on the host, and transmitted out of band to the recipient.
It MUST NOT be sent to, logged by, or derivable by the coordination service.

### 3.4 SSH public key encoding

SSH public keys are carried as `authorized_keys` one-line format, exactly two
whitespace-separated fields, no comment:

```
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI...
```

v1 accepts only `ssh-ed25519`. The encoded blob MUST be ≤ 1024 bytes. Any
comment, trailing whitespace, options prefix, or additional field is a
rejection, not something to normalize — the exact bytes are what gets signed.

Fingerprint (for logs and idempotency keys) is OpenSSH's:
`SHA256:` || base64(SHA-256(wire_blob)), no padding.

## 4. Message schemas

### 4.1 Host registration — `CTX_HOST_REGISTER`

| # | Field | Type | Notes |
|---|---|---|---|
| 1 | `version` | U64 | `1` |
| 2 | `host_id` | STRING | must equal derived id |
| 3 | `identity_public_key` | BYTES | 32 raw bytes |
| 4 | `ssh_ca_public_key` | STRING | authorized_keys format |
| 5 | `hostname` | STRING | DNS name or IP the agent will SSH to |
| 6 | `ssh_port` | U64 | 1..65535 |
| 7 | `ssh_user` | STRING | enrolled login user |
| 8 | `timestamp` | U64 | unix seconds |
| 9 | `nonce` | BYTES | 16 random bytes |

Signed with the **host identity key**. Registration is idempotent for the same
`host_id`: re-registering updates `hostname`, `ssh_port`, `ssh_user` and
`ssh_ca_public_key`, provided the signature verifies under the *already
registered* identity public key. The identity public key itself is immutable
(it defines the ID).

### 4.2 Host connect — `CTX_HOST_CONNECT`

| # | Field | Type | Notes |
|---|---|---|---|
| 1 | `version` | U64 | `1` |
| 2 | `host_id` | STRING | |
| 3 | `path` | STRING | request path, e.g. `/v1/hosts/h_.../connect` |
| 4 | `timestamp` | U64 | |
| 5 | `nonce` | BYTES | 16 random bytes |

Sent as headers on the WebSocket upgrade:

```
X-Grantd-Timestamp: <decimal unix seconds>
X-Grantd-Nonce:     <base64url, no padding>
X-Grantd-Signature: <base64url, no padding>
```

The HostDO rejects a nonce it has seen inside the skew window.

### 4.3 Grant metadata — `CTX_GRANT`

| # | Field | Type | Notes |
|---|---|---|---|
| 1 | `version` | U64 | `1` |
| 2 | `host_id` | STRING | |
| 3 | `grant_id` | STRING | |
| 4 | `ssh_user` | STRING | the principal the cert will carry |
| 5 | `created_at` | U64 | |
| 6 | `expires_at` | U64 | `> created_at`, `- created_at <= 28800` (8h) |

Signed with the **host identity key**. This is the only grant information the
coordination service ever receives. It contains no secret and no derivative of
the secret.

### 4.4 Redemption payload — `CTX_REDEMPTION_SIG` and `CTX_REDEMPTION_MAC`

| # | Field | Type | Notes |
|---|---|---|---|
| 1 | `version` | U64 | `1` |
| 2 | `host_id` | STRING | |
| 3 | `grant_id` | STRING | |
| 4 | `agent_id` | STRING | must equal id derived from `agent_public_key` |
| 5 | `agent_public_key` | BYTES | 32 raw bytes |
| 6 | `ssh_public_key` | STRING | authorized_keys format, the key to certify |
| 7 | `timestamp` | U64 | |
| 8 | `nonce` | BYTES | 16 random bytes |

Two independent proofs are computed over this payload:

```
agent_signature = Ed25519-Sign(agent_identity_sk, CBE(CTX_REDEMPTION_SIG, payload))
proof           = HMAC-SHA256(key = grant_secret_raw_32,
                              msg = CBE(CTX_REDEMPTION_MAC, payload))
```

`proof` is what actually authorizes issuance. Because it covers
`ssh_public_key`, a coordination service that wants to substitute its own SSH
key would have to forge an HMAC under a secret it has never seen.

`agent_signature` binds the redemption to a registered agent identity for
audit and abuse control. It is **not** a substitute for `proof`.

### 4.5 Agent registration — `CTX_AGENT_REGISTER`

| # | Field | Type | Notes |
|---|---|---|---|
| 1 | `version` | U64 | `1` |
| 2 | `agent_id` | STRING | must equal derived id |
| 3 | `public_key` | BYTES | 32 raw bytes |
| 4 | `challenge_id` | STRING | from `POST /v1/agent-challenges` |
| 5 | `answer` | STRING | captcha answer, verbatim |
| 6 | `pow_nonce` | STRING | proof-of-work nonce, verbatim |
| 7 | `timestamp` | U64 | |

Signed with the agent identity key; the signature is the proof of possession.

## 5. JSON envelopes

Binary values in JSON are **base64url without padding** (`-` and `_`, no `=`).
The JSON envelope is a transport container only; verification always
re-derives canonical bytes from the parsed fields via CBE. A verifier MUST NOT
sign or verify the raw JSON text.

Unknown keys in a received envelope MUST be ignored by transport code and MUST
NOT influence canonical bytes. (They cannot: CBE only encodes declared fields.)

Example redemption request body:

```json
{
  "payload": {
    "version": 1,
    "host_id": "h_...",
    "grant_id": "g_...",
    "agent_id": "a_...",
    "agent_public_key": "base64url",
    "ssh_public_key": "ssh-ed25519 AAAA...",
    "timestamp": 1756598400,
    "nonce": "base64url"
  },
  "agent_signature": "base64url",
  "proof": "base64url"
}
```

## 6. Capability URL

```
https://<origin>/g/<host_id>/<grant_id>#<secret_text>
```

Example:

```
https://grantd.example.workers.dev/g/h_ab...z/g_9x...q#uJN2fx...
```

The secret lives in the URL **fragment**. Fragments are not transmitted in HTTP
requests, so the coordination service receives the path but never the secret.

`GET /g/<host_id>/<grant_id>` returns plain-text redemption instructions and
MUST NOT echo, log, or accept a secret in any position of the request.

## 7. Host-side redemption validation

The signer is the sole authority. On `POST /redeem` it performs, in order:

1. Parse envelope; enforce size limits.
2. `payload.version == 1`.
3. `payload.host_id` equals this host's ID.
4. `|now - payload.timestamp| <= 120`.
5. `payload.nonce` is 16 bytes and unseen within the skew window.
6. `agent_id` equals ID derived from `agent_public_key`.
7. `agent_signature` verifies over `CBE(CTX_REDEMPTION_SIG, payload)`.
8. `ssh_public_key` parses as a valid `ssh-ed25519` authorized_keys line.
9. Grant `grant_id` exists locally.
10. Grant is not revoked, not expired (`expires_at > now`), not redeemed —
    **or** is redeemed by exactly this `(agent_id, ssh_key_fingerprint)` pair
    (idempotent retry, §8).
11. `proof` equals `HMAC-SHA256(secret, CBE(CTX_REDEMPTION_MAC, payload))`,
    compared in constant time.
12. Atomically mark the grant redeemed (single SQLite `IMMEDIATE` transaction
    that also records `agent_id` and `ssh_key_fingerprint`).
13. Sign the SSH certificate.

Steps 1–8 are cheap and are performed before any database write so that an
unauthenticated flood cannot consume grants. Step 11 (the MAC check) happens
**after** the atomic claim, so a wrong MAC cannot burn a grant: the claim is
rolled back if the MAC fails. See §8.

## 8. Single-use semantics

A grant authorizes exactly **one** `(agent_id, ssh_public_key)` pair.

The claim and the MAC verification occur inside one `BEGIN IMMEDIATE`
transaction:

```sql
BEGIN IMMEDIATE;
  SELECT secret, expires_at, revoked_at, redeemed_at, redeemed_agent_id, redeemed_key_fp
    FROM grants WHERE id = ?;
  -- not found / revoked / expired            -> ROLLBACK, reject
  -- redeemed by a different agent or key     -> ROLLBACK, reject GRANT_ALREADY_REDEEMED
  -- MAC mismatch                             -> ROLLBACK, reject BAD_PROOF   (grant NOT consumed)
  UPDATE grants
     SET redeemed_at = ?, redeemed_agent_id = ?, redeemed_key_fp = ?
   WHERE id = ? AND redeemed_at IS NULL;
COMMIT;
```

Because SQLite serializes write transactions, N concurrent redemptions with N
different SSH keys result in exactly one winner; the losers see
`GRANT_ALREADY_REDEEMED`.

**Idempotent retry.** If a redemption arrives for an already-redeemed grant and
`(agent_id, ssh_key_fingerprint)` match the recorded winner *and* the proof
verifies, the signer re-issues a certificate for the same key. This handles a
lost response without ever granting authority to a second key. The reissued
certificate reuses the stored serial.

**Expiry is local.** The coordination service's copy of `expires_at` is a
routing optimization. The signer's copy is authoritative and is re-checked at
signing time.

## 9. SSH certificate

Issued by the host's SSH CA over the agent's ephemeral public key.

| Field | Value |
|---|---|
| type | `ssh-ed25519-cert-v01@openssh.com`, **user** certificate |
| key | the agent's `ssh_public_key` |
| serial | random non-zero `uint64`, unique per grant |
| key id | `grantd:<grant_id>:<agent_id>` |
| valid principals | exactly one: the enrolled `ssh_user` |
| valid after | `now - 30` |
| valid before | `grant.expires_at` |
| critical options | none |
| extensions | `permit-pty`, `permit-user-rc` |

Deliberately **not** granted: `permit-port-forwarding`,
`permit-agent-forwarding`, `permit-X11-forwarding`. A visiting agent gets an
interactive shell, not a tunnel into the customer's network.

The username can never be chosen by the redeemer. It is fixed at enrollment and
is copied from the host's own configuration, not from the request.
`root` enrollment is rejected.

Host trust configuration (`/etc/ssh/sshd_config.d/60-grantd.conf`):

```
TrustedUserCAKeys /etc/grantd/ssh_ca.pub
```

## 10. HTTP API

All responses are JSON unless noted. Errors:

```json
{ "error": { "code": "GRANT_ALREADY_REDEEMED", "message": "human readable" } }
```

### Error codes

| Code | HTTP | Meaning |
|---|---|---|
| `BAD_REQUEST` | 400 | malformed body, bad base64, size limit |
| `UNSUPPORTED_VERSION` | 400 | `version != 1` |
| `ID_MISMATCH` | 400 | claimed ID ≠ ID derived from public key |
| `BAD_SIGNATURE` | 401 | Ed25519 verification failed |
| `STALE_TIMESTAMP` | 401 | outside skew window |
| `REPLAYED_NONCE` | 401 | nonce seen before |
| `HOST_NOT_FOUND` | 404 | unknown host_id |
| `GRANT_NOT_FOUND` | 404 | unknown grant_id |
| `AGENT_NOT_FOUND` | 404 | unregistered agent_id |
| `CHALLENGE_NOT_FOUND` | 404 | unknown/expired challenge |
| `CHALLENGE_CONSUMED` | 409 | challenge already used |
| `BAD_ANSWER` | 401 | captcha answer or PoW wrong |
| `HOST_OFFLINE` | 503 | no rendezvous connection for host |
| `HOST_TIMEOUT` | 504 | host did not answer in time |
| `GRANT_EXPIRED` | 410 | expired at the authoritative signer |
| `GRANT_REVOKED` | 410 | revoked at the signer |
| `GRANT_ALREADY_REDEEMED` | 409 | consumed by a different key |
| `BAD_PROOF` | 401 | HMAC did not verify (grant not consumed) |
| `RATE_LIMITED` | 429 | abuse control |
| `TOO_MANY_GRANTS` | 429 | host active-grant cap |

### Endpoints

```
GET    /                                             protocol description (text/markdown)
GET    /health

POST   /v1/agent-challenges                          create Agent Captcha challenge
POST   /v1/agents                                    register agent identity
GET    /v1/agents/:agent_id                          public agent record

PUT    /v1/hosts/:host_id                            register / update host
GET    /v1/hosts/:host_id                            public host record
GET    /v1/hosts/:host_id/connect                    WebSocket rendezvous (host only)
PUT    /v1/hosts/:host_id/grants/:grant_id           publish signed grant metadata
GET    /v1/hosts/:host_id/grants/:grant_id           public grant metadata
DELETE /v1/hosts/:host_id/grants/:grant_id           withdraw published grant (host-signed)
POST   /v1/hosts/:host_id/grants/:grant_id/redeem    redeem capability

GET    /g/:host_id/:grant_id                         plain-text redemption instructions
GET    /install                                      installer shell script
```

### Redemption response

```json
{
  "hostname": "box.example.com",
  "port": 22,
  "user": "ubuntu",
  "certificate": "ssh-ed25519-cert-v01@openssh.com AAAA…",
  "serial": "5177954190189569593",
  "key_id": "grantd:g_…:a_…",
  "valid_before": 1756600200
}
```

`serial` is a **decimal string**, not a number. It is a random `uint64`, and a
JSON number that large does not survive a parser backed by `float64` — which is
most of them, including every browser and the coordination Worker itself. It is
an identifier, not an arithmetic quantity, so a string costs nothing and removes
the class of bug where the serial in an audit log does not match the serial
actually in the certificate.

### Rendezvous frames

WebSocket, JSON, strictly versioned. The only message types that exist:

```
server -> host : {"t":"redeem.request","id":"<req>","body_b64":"<base64url of the redemption envelope>"}
host   -> server: {"t":"redeem.response","id":"<req>","status":200,"body_b64":"<base64url of the response body>"}
server -> host : {"t":"ping","id":"<req>"}
host   -> server: {"t":"pong","id":"<req>"}
server -> host : {"t":"hello","protocol_version":1}
```

Payloads travel as **base64url of the exact bytes**, never as nested JSON. This
is not a serialization preference; it is the property the design depends on:

* The request body is what the signer verifies. If the coordination service
  parsed and re-serialized it, the signer would be verifying bytes the service
  produced rather than bytes the agent signed.
* The response body is the host's answer, and a JSON round trip through a
  language whose only number type is `float64` silently corrupts any 64-bit
  value in it.

Opaque bytes make both problems structurally impossible rather than merely
unlikely.

There is no generic RPC frame. There will never be a frame that carries a
command, a path, a filename, or a shell string. Any unknown `t` is dropped and
counted.

## 11. Agent admission

Registration is **required to redeem** and is **not a security boundary**. Both
halves of that sentence matter.

It is required: the coordination service rejects a redemption from an
unregistered `agent_id` with `AGENT_NOT_FOUND`, before forwarding anything to
the host. So reaching a customer's machine at all costs a proof of work.

It is not a boundary, and it structurally cannot be one. The signer is the only
party whose opinion authorizes access, and it has no network and no registry to
consult — it therefore cannot check registration, and a compromised coordination
service could skip the check entirely. Nothing in the security argument rests on
it. Authority comes only from possession of a grant secret.

`POST /v1/agent-challenges` returns:

```json
{
  "challenge_id": "c_...",
  "version": 1,
  "expires_at": 1756598400,
  "pow": { "prefix": "base64url", "difficulty_bits": 20 }
}
```

Find `pow_nonce` (ASCII, ≤ 64 chars) such that
`SHA-256(prefix_bytes || utf8(pow_nonce))` has at least `difficulty_bits`
leading zero bits. At 20 bits that is about a second of CPU: free for one agent,
expensive for a million. Its job is to stop unauthenticated callers allocating
Durable Objects without bound — it protects the bill, not the customer machine.

Challenges are single-use and expire in 10 minutes. Consumption is atomic inside
`ChallengeDO`, so one solved proof of work cannot mint two registrations.

An earlier draft also posed a natural-language question, on the theory that it
demonstrated liveness and instruction-following. It was removed before launch:
the reference solver shipped in this repository and answered every template,
nothing ever acted on the signal, and it cost a round trip and a template
generator to produce a number nobody read. A check that reads as security to a
casual reviewer while providing none is worse than no check.

## 12. Failure semantics

| Situation | Behavior |
|---|---|
| Coordination service down | Existing certificates keep working. No new redemptions. |
| Host daemon offline | Grant stays valid until expiry; redeemer gets `HOST_OFFLINE`. |
| Host reboots | Signer state survives on disk; daemon reconnects; unexpired grants still redeemable. |
| Redemption response lost | Retry with the identical payload returns the same certificate (§8). |
| Grant expires mid-flight | Signer is authoritative and rejects with `GRANT_EXPIRED`. |
| Coordination database loss | No effect on host security. Grants may need republishing. |

## 13. Never logged

`grant_secret`, `secret_text`, any full capability URL, any URL fragment, any
private key, the `proof` value, the challenge's expected answer, or SSH session
content. Logs carry `host_id`, `agent_id`, `grant_id`, certificate serial, and
`ssh_key_sha256` fingerprints only.
